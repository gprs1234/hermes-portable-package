# PLAN Factory — 從點子到全自治的誕生系統

**日期**: 2026-05-01
**核心概念**: PLAN 不是「一個監控腳本」，是「一個有完整生命週期的自治個體」

---

## 為什麼需要 PLAN Factory

Owner 的現實：
- 一天可能 1-3 個新點子
- 不一定在電腦前
- 每個點子對應一個項目，需要 bot/媒介/資料管理
- 點子是臨時的，但系統應該是持久的
- 現在的方式是「想到就建，忘了就翻到才修」

PLAN Factory 要解決的：
- 從「點子」到「全自治系統」不需要人類動手
- 每個 PLAN 自己決定用什麼技術、什麼媒介、什麼資料管理
- 每個 PLAN 自己監控自己、自己修復、自己報告

## PLAN 的完整生命週期

```
[誕生] Owner 說：「我想做一個材料管理系統」
  │
  ▼
[Phase 1: 需求分析] Hermes 自動問自己：
  │  - 這個系統的使用者是誰？（Owner 獨自？有員工？有客戶？）
  │  - 使用場景？（手機看？電腦操作？倉庫掃碼？）
  │  - 資料量？（每天 10 筆？每天 1000 筆？）
  │  - 需要即時嗎？（每秒？每小時？每天？）
  │  - 跟現有系統的關聯？（接 POS？接 Trading？獨立？）
  │
  ▼
[Phase 2: 媒介選擇] 自動決定通訊管道：
  │  ┌─────────────────────────────────────────┐
  │  │ 判斷規則：                               │
  │  │   需要隨時看 → Telegram Bot              │
  │  │   需要圖表 → Web Dashboard               │
  │  │   需要多人協作 → Notion/Google            │
  │  │   需要行動裝置 → TG + 簡單 Web           │
  │  │   需要複雜操作 → 專用 App/Web UI          │
  │  │   只需要記錄 → 本地 JSON/SQLite           │
  │  └─────────────────────────────────────────┘
  │
  ▼
[Phase 3: 資料管理] 自動選擇資料層：
  │  ┌─────────────────────────────────────────┐
  │  │ 判斷規則：                               │
  │  │   需要搜尋/篩選 → SQLite                 │
  │  │   需要協作/分享 → Notion API / Google     │
  │  │   需要離線 → 本地 JSON/CSV               │
  │  │   需要即時同步 → WebSocket + SQLite       │
  │  │   資料量大 → PostgreSQL                   │
  │  │   資料量小 → JSON 就好                    │
  │  └─────────────────────────────────────────┘
  │
  ▼
[Phase 4: 技術棧] 自動選擇：
  │  ┌─────────────────────────────────────────┐
  │  │ Telegram Bot → python-telegram-bot       │
  │  │ Web Dashboard → Flask/FastAPI + HTML     │
  │  │ API → FastAPI                            │
  │  │ 桌面 → Electron / Python GUI             │
  │  │ 定時任務 → Cron Job                      │
  │  │ 資料處理 → Python + pandas               │
  │  └─────────────────────────────────────────┘
  │
  ▼
[Phase 5: 自治規則] 自動定義：
  │  ┌─────────────────────────────────────────┐
  │  │ 什麼情況自己處理：                       │
  │  │   - 服務掛掉 → 自動重啟                  │
  │  │   - 資料格式錯誤 → 自動修正              │
  │  │   - 重複性任務 → 沉澱成 skill            │
  │  │                                          │
  │  │ 什麼情況告訴主人：                       │
  │  │   - 需要商業決策                         │
  │  │   - 結構性崩潰                           │
  │  │   - 涉及金錢/合約                        │
  │  │   - 需要外部資源（API key、帳號）        │
  │  │                                          │
  │  │ 什麼頻率報告：                           │
  │  │   - 正常 → 每天一次摘要                  │
  │  │   - 異常 → 即時推播                      │
  │  │   - 嚴重 → 緊急通知 + 停止自動操作       │
  │  └─────────────────────────────────────────┘
  │
  ▼
[Phase 6: 建造] 自動生成：
  │  - Bot 代碼（如果有 Telegram 需求）
  │  - Dashboard（如果有 Web 需求）
  │  - 資料層（SQLite/JSON/API）
  │  - 監控腳本（health check）
  │  - Worker Skills（維護程序）
  │  - Cron Job（定時巡邏）
  │  - 文件（README、API 文檔）
  │
  ▼
[Phase 7: 登記] 自動註冊到 PLAN Registry：
  │  - plan_id、名稱、領域
  │  - 心跳路徑、指令路徑
  │  - 依賴圖（跟哪些 PLAN 有關）
  │  - 自治規則摘要
  │
  ▼
[Phase 8: 運轉] 自治運行：
  │  - 每天自動巡邏
  │  - 自動修復
  │  - 自動報告
  │  - 經驗沉澱成 skill
  │  - 問題升級時通知主人
  │
  ▼
[Phase 9: 進化] 持續改進：
     - 使用者行為分析 → 優化介面
     - 問題模式識別 → 建立預防機制
     - 功能使用頻率 → 砍掉不用的功能
     - 新需求出現 → 自動擴展
```

## Owner 使用習慣資料庫

PLAN Factory 要知道主人的習慣才能做出正確的媒介選擇：

```yaml
Owner_profile:
  主要裝置: 手機（Telegram 為主）
  電腦使用: 不固定，不一定在電腦前
  偏好介面: Telegram > Web > CLI
  偏好通知: 即時推播（重要事項）、每日摘要（一般事項）
  語言: 繁體中文
  時區: UTC+8
  活躍時段: 不固定
  技術能力: 可以操作 Telegram，不寫代碼
  厭惡: 「先不管」「有事叫我」、被動等待
  喜歡: 自動執行、做完回報、跨領域類比
```

## 範例：材料管理系統的 PLAN 規劃

```
Owner:「我想做一個材料管理系統」

Hermes 自動分析：
  Q: 使用者是誰？
  A: Owner 自己 + 可能有員工 → 需要多人存取

  Q: 使用場景？
  A: 倉庫進出貨、即時查詢庫存 → 手機為主

  Q: 需要即時嗎？
  A: 進出貨時要即時更新 → 需要即時

  Q: 資料量？
  A: 中小規模（每天幾十筆）→ SQLite 夠用

  Q: 跟現有系統關聯？
  A: 可能接 POS → 需要 API 介面

Hermes 自動決定：
  媒介: 
    - Telegram Bot（手機查詢 + 進出貨通知）
    - Web Dashboard（庫存總覽 + 報表）
  資料層: SQLite + JSON 備份
  技術棧: 
    - FastAPI（API 層）
    - Telegram Bot（查詢 + 操作）
    - Flask（Dashboard）
  自治規則:
    - 庫存低於閾值 → 自動通知 Owner
    - 服務掛掉 → 自動重啟
    - 每日庫存摘要 → TG 推播
    - 每月報表 → 生成 PDF

Hermes 自動建造：
  1. 建目錄 ~/projects/material_mgmt/
  2. 寫 bot（查庫存、登記進出貨）
  3. 寫 API（CRUD 材料、庫存查詢）
  4. 寫 Dashboard（庫存總覽）
  5. 寫監控腳本
  6. 設 cron job
  7. 登記 PLAN Registry
  8. 通知 Owner:「材料管理系統已上線，TG Bot: @xxx_bot」
```

## PLAN Factory 自己也是一個 PLAN

```
PLAN Factory（meta-PLAN）
  │  - 管理所有 PLAN 的誕生過程
  │  - 維護 Owner 使用習慣資料庫
  │  - 維護技術選型資料庫
  │  - 維護媒介選擇規則
  │  - 每誕生一個新 PLAN，自動更新依賴圖
  │
  ▼
PLAN Registry
  │  - 登記所有 PLAN
  │  - 監控所有 PLAN
  │
  ▼
各事業體 PLAN
     - Arena
     - Trading
     - POS
     - 材料管理
     - ...（將來的點子）
```
